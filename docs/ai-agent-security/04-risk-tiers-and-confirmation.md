# 04 — Risk Tiers & Confirmation Model

Risk tier is a **static property of each tool definition**, assigned at registration and reviewed like code. The policy engine can escalate a tier at runtime (bulk targets, untrusted-content influence, large amounts) but can never lower one. The model has no say in tiering.

## Tier table

| | Tier 0 — Informational | Tier 1 — Read-only | Tier 2 — Low-risk writes | Tier 3 — Sensitive writes | Tier 4 — High-impact / irreversible |
|---|---|---|---|---|---|
| **Examples** | Product questions, feature explanations | `get_customer`, `search_orders`, `generate_report` | `add_note`, `create_draft`, `create_support_ticket`, `update_preference` | `update_contact_details`, `send_approved_email`, `update_workflow_status`, `assign_task` | `request_refund`, `cancel_order`, `export_customer_records`, `deactivate_account` |
| **Auth level** | Valid session | Valid session | Valid session | MFA-backed session | MFA + fresh step-up (≤5 min) |
| **User confirmation** | No | No | No (undo offered) | **Yes — structured preview + explicit confirm** | **Yes — preview + confirm** |
| **Preview required** | — | — | No | Yes (before/after diff) | Yes (full impact statement) |
| **Step-up auth** | No | No | No | For escalated cases | **Yes** |
| **Human approval (second person)** | No | No | No | No | Above thresholds (amount, record count) or per policy |
| **Logging** | Minimal (metrics) | Standard audit | Full audit | Full audit + confirmation evidence | Full audit + confirmation + approval chain, alert on execution |
| **Rate limits** | Loose | Per-user query caps, row caps | Per-user hourly caps | Tight per-user daily caps | Very tight (e.g., single-digit/day) + velocity alerts |
| **Rollback** | n/a | n/a | Undo (delete note/draft) | Required — prior values stored, reversible or compensable | **Compensating transaction mandatory** or action is soft (request, soft-delete) — truly irreversible actions are redesigned until reversible |

Escalation rules (doc 03): untrusted-content influence bumps +1 tier; `affectedRecordCount > N` or external recipients > N bumps to ≥3; amount > threshold forces `require_approval`.

## Confirmation categories

| Category | Treatment |
|---|---|
| Informational response | None |
| Read-only action | None (audited) |
| Reversible write | Execute + visible undo |
| External communication | Preview showing exact recipients + rendered content; confirm |
| Financial action | Preview with amount, account, impact; confirm + step-up; approval above threshold |
| Sensitive-data access | Purpose-bound; masked by default, unmask is itself a confirmed action |
| Bulk operation | Preview with exact count + sample of affected records; confirm + step-up; approval above caps |
| Destructive / irreversible | Soft/staged only; confirm + step-up + (usually) second approver |

## The action preview

Generated by the **gateway from the system of record — never composed by the model** (a model-written preview could be injected or hallucinated). Contents:

```
Action:            update_contact_details
Target:            Customer #C-10422 — "Acme Industries" (tenant: acme-prod)
Fields changing:   phone
Current value:     +972-3-555-0100
Proposed value:    +972-3-555-0177
External sends:    none
Financial impact:  none
Side effects:      customer notified of contact change (standard policy)
Reversible:        yes — previous value retained 90 days
```

## Confirmation mechanics (why conversation text is not consent)

"Yes, go ahead" in chat is forgeable by injection, ambiguous, and replayable. Instead:

1. Gateway computes `action_hash = SHA-256(canonical_json({tool, params, target_ids, resource_versions}))`.
2. Issues a **confirmation token**: HMAC-signed payload `{action_hash, user_id, session_id, issued_at, ttl: 120s, nonce}`; stored server-side as unconsumed.
3. UI renders the preview with a native **Confirm** button (not a chat message). Clicking sends the token back over the authenticated channel.
4. Executor validates: signature, TTL, session match, **single-use** (consume-on-check, atomically), and that `action_hash` still matches — including `resource_versions`, so a record changed since preview forces a fresh preview (optimistic locking, doc 07).
5. Only then does execution proceed. The model never sees or transmits the token; a model message claiming "user confirmed" is inert.

Step-up (Tier 4): the confirm button first routes through re-authentication (WebAuthn/TOTP); the step-up assertion is attached to the confirmation and checked by policy. Second-approver: action parks in `pending_approval`; a different human with the approver role reviews the same gateway-generated preview in an approval queue; approval is its own audited, signed event.

## Preventing stage-skipping

The pipeline (interpret → plan → retrieve → validate → authorize → classify → confirm → execute → verify → audit) is enforced by types and construction, not by prompting:

- The only exported way to run a tool is `executor.execute(ExecutableAction)`, and an `ExecutableAction` can only be constructed by the gateway pipeline — its constructor requires a `PolicyDecision`, an `AuthzDecision`, and (when policy demands) a consumed `ConfirmationToken`. Hand-rolled objects fail signature verification.
- Audit write is *inside* `execute()`, before and after the handler; if the audit store is unavailable, Tier ≥2 execution fails closed.
- Model output is parsed into either `say(text)` or `propose(toolCall)` — there is no third variant, so there is nothing the model can emit that reaches a handler directly.
- CI red-team tests (doc 10) assert each bypass attempt fails: forged tokens, replayed tokens, stale versions, unregistered tools, confirmation-in-text.
